# **07\_EXECUTION\_TRACE.md**

# **Execution Trace Specification**

**Version:** 1.0

---

# **Purpose**

The Execution Trace is the single source of truth for everything that happens inside the CRAG pipeline.

The frontend **must never infer execution state, node outputs, branch decisions, or timing**.

Instead, the backend emits structured trace events as the pipeline executes, and the frontend simply renders them.

This creates a clean separation between business logic and visualization.

---

# **Design Principles**

The execution trace follows these principles.

* Backend owns all execution state.  
* Frontend only renders received data.  
* Every node emits a structured event.  
* Every event has the same base schema.  
* Node-specific outputs are stored inside the output object.  
* Failed nodes emit the same schema with an error section.  
* The entire trace can be replayed after execution.

# **Common Node Fields**

| Field | Description |
| ----- | ----- |
| node\_id | Unique identifier |
| node\_name | Internal backend name |
| display\_name | Human readable name |
| type | retrieval, evaluation, search, generation etc |
| status | Current node state |
| started\_at | ISO timestamp |
| completed\_at | ISO timestamp |
| duration\_ms | Execution duration |
| input | Input received by node |
| output | Output generated by node |
| metadata | Performance/debug information |
| error | Error object if failed |

}

---

# **Decision Path**

The backend explicitly returns the selected branch.

Correct

{  
    "decision\_path":"CORRECT"  
}

Ambiguous

{  
    "decision\_path":"AMBIGUOUS"  
}

Incorrect

{  
    "decision\_path":"INCORRECT"  
}

The frontend never decides which branch to animate.

It simply follows the value returned by the backend.

---

# **Frontend Rendering Rules**

The frontend must never compute pipeline state.

Instead,

it renders exactly what the backend provides.

Examples

If

status \= RUNNING

↓

Animate node.

If

status \= SUCCESS

↓

Mark node green.

If

status \= FAILED

↓

Mark node red.

If

status \= SKIPPED

↓

Fade node.

---

# **Chat Processing Indicator**

The backend also controls the temporary status shown in the chat.

Example sequence

{  
    "display\_message":"Retrieving..."  
}

↓

{  
    "display\_message":"Evaluating..."  
}

↓

{  
    "display\_message":"Generating..."  
}

Only one status message exists at a time.

When generation completes,

the backend emits

{  
    "display\_message":null  
}

The frontend removes the temporary indicator and displays the final answer.

---

# **Node Inspector Contract**

When a graph node is clicked,

the frontend simply renders

selected\_node.output

and

selected\_node.metadata

No additional processing or formatting logic should be required beyond presentation.

---

# **Event Ordering**

Events are emitted strictly in execution order.

Example

Trace Created

↓

Retriever Started

↓

Retriever Completed

↓

Evaluator Started

↓

Evaluator Completed

↓

Knowledge Refinement Started

↓

Knowledge Refinement Completed

↓

Knowledge Search Started

↓

Knowledge Search Completed

↓

Generator Started

↓

Generator Completed

↓

Trace Completed

This ordering allows the frontend to replay or animate the entire pipeline exactly as it occurred.

---

# **Design Philosophy**

The Execution Trace is the contract between the backend and frontend.

The backend owns all execution logic, state transitions, branch decisions, node outputs, and timing.

The frontend owns only presentation.

This architecture ensures that the visualization always reflects the true pipeline execution and can evolve independently of the underlying business logic.
